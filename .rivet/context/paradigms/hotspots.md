## Guidelines

**How to read the score.** It is `fan_in * churn` divided by the largest
`fan_in * churn` in the repo — a rank within *this* snapshot, not a measurement.
`internal/capabilities/builtins.go` scores 1.00 because it is currently the top
file, not because it crossed any threshold. Comparing a score against another
repo, or against this table after a refactor, is meaningless; only the ordering
within one run carries information.

**The product hides which risk you're facing.** `internal/schema/types/types.go`
(27 x 1) and `internal/config/config.go` (9 x 3) both score 0.50 and are not
remotely the same problem: one is a wide blast radius almost never touched, the
other a narrower one touched constantly. Read the two columns; ignore the product.

**Fan-in is a property of the Go package, not the file.** recon resolves a Go
import to *every* source file in the imported package's directory, so all eight
non-test files in `internal/context/` carry fan-in 12 — the count of files importing the
package. `internal/context/runbook.go` is not depended on by twelve files; its
package is. Within one package, ranking is therefore driven entirely by churn.
Splitting a package changes every fan-in number in it without changing any code.

**What the numbers do not count:**

- Only intra-module imports resolve — anything not prefixed with this repo's
  module path is dropped, so stdlib and third-party edges are invisible.
- Test files count as *importers* but never receive fan-in (import targets are
  filtered to source files). Four of the twelve importers of `internal/context`
  are `_test.go` files.
- Churn is the number of commits touching the file within the **last 500
  commits**, and commits touching more than 50 files are discarded wholesale as
  merges/reformats. Code only ever changed in big sweeps reads as churn 0.

**Absence from this table means nothing.** A zero on either factor makes the
product zero, and zero-scoring files are dropped from the list entirely. Every
test file, every brand-new file nothing imports yet, and `cmd/rivet/main.go` —
the process entrypoint — can never appear here regardless of how risky they are.

**The table is frozen.** `rivet context scaffold` never overwrites an existing
document, so these numbers date from the day the doc was created and drift
silently thereafter. For current values run `recon.hotspots`; to regenerate the
table, delete this file and re-scaffold. The "High-risk files" blocks in the
domain docs come from the same run, filtered to files inside the domain's
directory scoring above 0.05.

When modifying any file listed above:
- Check the fan-in count — that many files depend on this module
- Run the full test suite, not just the file's own tests
- Consider using `recon related <file>` to find affected files
